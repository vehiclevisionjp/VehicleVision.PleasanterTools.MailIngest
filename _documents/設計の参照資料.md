### メール接続の保護と認証（2026-10-22 追記）

`SecureSocketOptions.None` は暗号化なし、`SslOnConnect` は接続直後の TLS、
`StartTls` は昇格非対応なら失敗する。`Auto` / `StartTlsWhenAvailable` は平文継続があり得る。
本ツールは `None` / `StartTls` / `Tls` の 3 設定に限定し、後者を `SslOnConnect` へ対応づける設計。
既定 `Tls` と平文の明示許可は本ツールの判断であり、MailKit の既定値の説明ではない。
RFC 8314 は暗黙 TLS を推奨し、POP3 995 / IMAP 993、証明書検証とピン留めを説明している。
平文許可は旧環境への互換性のための明示例外であり、RFC の推奨と同等の安全性を主張しない。
RFC 2595 は POP3 STLS / IMAP STARTTLS による昇格と、SASL PLAIN がパスワードを含む形式を定義する。

MailKit README は SASL PLAIN / LOGIN / CRAM-MD5 等、POP3 APOP と USER/PASS を列挙する。
固定版クライアントでは POP3 は APOP・SASL・USER/PASS、IMAP は SASL から LOGIN の経路がある。
`AuthenticationMechanisms` の削除だけで非 SASL の方式まで禁止できるとは扱わない。
接続前の `ServerCertificateValidationCallback` で証明書検証を差し替える経路も確認した。
本ツールの方式別制御と限定的な未信頼チェーン許可・SHA-256 ピンは設計案であり、実装検証は未実施。
無条件に全証明書を許可するサンプルは採用しない。3 モードとも実サーバ動作は未確認。

### Core は別枠の自社部品

Core の `LICENSING.md` は **AGPL-3.0-or-later OR LicenseRef-PMC-Commercial**。
MIT 等の寛容 OSS として表へ混ぜない。
Core.Data / .Mail / .Web を使うときは、デュアル提供を維持する許諾根拠を確認する。
Core の公開例があるだけで、本ツールへ商用再許諾できると断定しない。

さらに Core.Data は SqlClient を参照し、Core の NOTICE は
`Microsoft.Data.SqlClient.SNI.runtime 7.1.0` を **Microsoft 独自許諾**として記載している。
[配布元の当該版ライセンス][sni-license] にも再頒布・利用者条件等があり、MIT / BSD / Apache ではない。
Core 側で認めた例外を本ツールの「寛容依存のみ」へ無断で持ち込まない。
SQLite だけを使ってもパッケージ参照・配布物から当該依存が外れるとは限らない。

**第 2 段階のブロッカー**として、Core の依存分割による回避、
本ツールで例外を認めるかのレビュー、または状態方式の再検討が必要。
今回の設計 PR ではどの例外も承認せず、パッケージ参照を追加しない。
他の Core 推移依存の個別ライセンス全件監査も今回は未実施。
採用時は公開 NuGet の依存グラフと最終配布物まで確認する。

### 採用時の作業

本 PR の候補はまだ実依存ではないので、実配布の NOTICE / NuGet ロックへ先行追加しない。
