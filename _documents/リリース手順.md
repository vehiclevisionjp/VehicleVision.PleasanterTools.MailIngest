# リリース手順

## 版

版の単一情報源は `Directory.Build.props` の `VersionPrefix`。セマンティックバージョニングに従い、1.0.0 未満は互換を保証しない。

## 手順

1. `develop` で `VersionPrefix` を上げ、`master` へ PR を出してマージする
2. Actions の「リリースタグ作成」を `master` から実行する。最初は `dry_run` のまま版だけを検証する
3. 問題なければ `dry_run` を外して実行する。必須チェックの成功を確認してから、GitHub App のトークンで `vX.Y.Z` タグを作る
4. タグを契機に「Release」ワークフローが、検証、配布 ZIP と SHA-256 の作成、GitHub Releases への公開を行う

`vX.Y.Z-rc.1` のようにハイフン付きの版はプレリリースとして公開する。

## 公開前の確認

- `LICENSE` と `NOTICE` が現状と合っている
- 配布物に設定ファイル・秘密・参照ソース・Git メタデータが入っていない（`scripts/package.ps1` が検査する）
- 参照ソースの取得はリリースの前提にせず、CI からも取得しない
- 商用公開でデュアルライセンスにする場合は [ライセンス](ライセンス.md) の手順が済んでいる

## 移行・注意

状態 DB の移行は、運用者が `migrate` で適用する（確認は `migrate-status`。未適用があれば終了コード 1）。`run` は未適用の移行があると起動しない。

- **Core 0.3.0 以降へ上げると、共有移行 M10008・M10009 が増える。** M10008 が空の表 `Core_AdminPasskeys`・`Core_AdminPasskeyChallenges` を作り、M10009 が `Core_AdminSessions` に NULL 可の `Via` 列を足す。既存の行と挙動は変わらない
- 移行を実行する DB ユーザーには、表の作成と列の追加（`CREATE TABLE`・`ALTER TABLE`）の権限が要る。実行用と通常の取り込み用でユーザーを分けている場合は、実行用で `migrate` を回す
- 上げたあと、取り込みを再開する前に `migrate-status` で未適用が無いことを確認する
- SQLite の空 DB で `migrate` を実行し、M0001 と M10001〜M10009 の全 10 件が適用されることを確認済み（SQL Server・PostgreSQL・MySQL は未確認）
